# RCA — Sign-in redirect loop on www.hireavatar.co (app "brandface")

**Deployment:** brandface · active run `1f0e32bb-98a1-4b58-8407-6dbb2f499073` · frontend_type=cloudflare · tier_0
**Symptom:** After Google / email+password login (Emergent-managed Clerk), users are bounced back to /sign-in (redirect loop) on the live custom domain. Preview works.

## Verdict
Everything on the Emergent/server side is healthy. The loop is caused by the **production Clerk instance not recognizing the custom domain**: it is still bound to the original `brandface.emergent.host` and does not list `www.hireavatar.co` / `hireavatar.co` as an allowed domain/origin. Clerk therefore never establishes a first-party session on the new domain, so the SPA (`<Show when="signed-out"><Navigate to="/sign-in"/></Show>`) perpetually sees the user as signed-out.

## What I checked (answers to the 4 questions)

### (1) Which Clerk keys/instance the prod build uses + allowed origins
- Production runs a **production Clerk instance** (`pk_live_…`). Proven by behaviour: the backend relay `/api/__clerk/*` only serves when the publishable key starts with `pk_live_` (`clerk_auth.py::_is_production()`), and the live logs show `/api/__clerk/v1/client`, `/v1/environment`, `/v1/oauth_callback` all returning 200/303. Preview uses the dev instance `pk_test_…` = `meet-kiwi-9413.clerk.accounts.dev` (from preview `backend/.env`).
- The publishable key is served at runtime from `GET /api/clerk/config` (returns `publishable_key` + `proxy_url`), and the frontend starts `<ClerkProvider proxyUrl=…>`. Zero-DNS proxy: the Frontend API is relayed through `https://<host>/api/__clerk`, and `clerk_proxy` sets `Clerk-Proxy-Url: https://<x-forwarded-host>/api/__clerk`.
- **Allowed origins / domain binding: could NOT be verified by me (lives in the Clerk dashboard, no tool access).** Inferred from the evidence below that `www.hireavatar.co` is NOT a registered domain of this production instance — it is still the originally-provisioned `brandface.emergent.host`. Custom domains were attached in the Emergent panel *after* first deploy; attaching a domain there does not reconfigure the Clerk production instance.

### (2) REACT_APP_BACKEND_URL / do /api calls reach the backend
- `REACT_APP_BACKEND_URL = https://www.hireavatar.co` — **verified** via list_secrets (matches_expected=true). Same origin as the site. Correct.
- /api calls reach the backend: live logs show `/api/clerk/config` 200, `/api/__clerk/*` 200/307, `/api/me` 200 — all from Cloudflare edge IPs on the live domain. Routing is fine.
- CORS_ORIGINS = `*` (verified matches_expected). Irrelevant here (same-origin), not the cause.

### (3) Backend /api/me after login
- **No 401s and no 403s anywhere** in the last 24h. `/api/me` returns **200**. Backend token verification works.
- Note on the azp/issuer hypothesis: `clerk_auth.py::verify_session_token` does `jwt.decode(token, key, algorithms=["RS256"], leeway=5)` with **no audience/issuer/azp check**. So an azp (authorized-parties) or issuer mismatch would NOT produce a 401 here, and in fact none occurred. The backend is not the problem.

### (4) Apex redirect
- `hireavatar.co` (apex) does **NOT** redirect to www: `root_redirect_enabled=false` on both domains (list_domains). Both domains are `verified=true`, `ssl_status=active`, DNS linked (check_domain_status). Users who land on the apex use a second origin that also will not have a Clerk session.

## Root cause
The production Clerk instance is still scoped to `brandface.emergent.host`. On `www.hireavatar.co` the Clerk handshake/environment calls succeed through the relay, but the production instance will not issue/accept a first-party session cookie for an un-registered domain, so `getToken()` / Clerk client state stays signed-out after OAuth → `<Navigate to="/sign-in">` loop. Dev instance (preview) is permissive about origin, which is why preview works.

## What must change
1. **(Platform / Emergent-managed Clerk)** Update the production Clerk instance to add `www.hireavatar.co` (primary) and `hireavatar.co` as allowed domains / origins, and point the proxy configuration (Clerk-Proxy-Url) at `https://www.hireavatar.co/api/__clerk`. Since this Clerk instance is Emergent-managed, the user cannot edit it from the deployment panel — Emergent must re-bind the instance to the new custom domain (or the user must do it in the Clerk dashboard if they own it).
2. **(User — Domains panel)** Enable apex→www root redirect for `hireavatar.co` so there is a single canonical origin (`www`), avoiding a second, un-registered Clerk origin.

## NOT the cause (ruled out with evidence)
- Wrong REACT_APP_BACKEND_URL / cross-origin /api — ruled out (same-origin, 200s).
- Backend 401/403, azp/issuer mismatch — ruled out (no 401/403; backend doesn't check azp/issuer; /api/me=200).
- Preview `pk_test` key leaking into prod — ruled out (prod relay active ⇒ `pk_live_`).
- CORS — ruled out (`*`, same-origin).
- No code fix was reproduced in the sandbox; the fix is in Clerk instance config, which cannot be reproduced without the live Clerk dashboard.
